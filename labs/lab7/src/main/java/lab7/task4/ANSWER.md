Задание 4. Producer–consumer

RequestPipeline передаёт неотрицательные id заявок через ArrayBlockingQueue. Каждый список входа обслуживает отдельный producer, несколько consumers извлекают заявки и добавляют их в результат. Порядок обработки между потоками не фиксирован; повторы входных id остаются отдельными заявками.

put блокирует producer при заполнении ограниченной очереди, пока consumer не освободит место: это backpressure. take ожидает заявку без busy waiting. После завершения всех producers в FIFO-очередь добавляется по одному STOP (-1) на consumer. Поэтому все заявки извлекаются перед сигналами завершения. Каждый consumer выходит после первого STOP. Входные отрицательные id запрещены.

Обработка сразу перенесена на ExecutorService: отдельный дублирующий вариант на ручных Thread не нужен. Для этого блокирующего сценария размер пула равен числу producers + consumers (при пустом входе есть один запасной поток). Все роли могут выполняться одновременно; маленький общий пул мог бы заняться только заблокированными producers. Для CPU-bound обработки разумный начальный размер — Runtime.getRuntime().availableProcessors(), но блокирующие producers тогда следует вынести отдельно. Имена потоков requests-N.

Future.get и отправка STOP имеют предел ожидания 5 секунд на операцию. При ошибке вызывается shutdownNow; finally всегда вызывает общий Pools.shutdown: shutdown, ожидание до 2 секунд, при необходимости shutdownNow и ещё до 2 секунд ожидания. Прерывание восстанавливается. Все блокирующие операции задач реагируют на interrupt. shutdownNow запрашивает остановку, а не принудительно убивает произвольный Java-код.

Тесты проверяют 200 заявок при ёмкости 1, несколько producers/consumers, пустой вход, неверные аргументы и прерывание координатора. Ограничение очереди относится к передаче заявок; демонстрационный результат накапливается в списке.
