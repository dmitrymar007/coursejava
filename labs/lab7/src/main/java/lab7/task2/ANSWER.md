Задание 2. Флаг остановки и visibility

PlainWorker содержит гонку чтения и записи stopped: между потоками нет отношения happens-before для этого флага. Worker может увидеть запрос, но язык не гарантирует видимость. Thread.onSpinWait — подсказка процессору, она не заменяет синхронизацию.

main запускает обычный и volatile-вариант. CountDownLatch сообщает о запуске, после чего основной поток запрашивает остановку. Если запрос не замечен за секунду, Future.cancel(true) прерывает worker. Проверка interrupted нужна для аварийного выхода. Остановка обычного варианта в отдельном запуске не доказывает корректность; timeout тоже не доказывает причину задержки. Надёжно требовать зависания ошибочного варианта в JUnit нельзя.

В VolatileWorker запись stopped happens-before последующего чтения этого volatile-поля. Это обеспечивает видимость запроса без блокировки. Но volatile int counter и counter++ всё равно допускают потерянные обновления: чтение и запись по отдельности не делают всю составную операцию атомарной. Для неё нужны synchronized либо атомарная read-modify-write операция, например AtomicInteger.incrementAndGet().

Тесты проверяют остановку через volatile и аварийное прерывание обычного worker. У чистого worker нет полезной работы: цикл здесь нужен только для изучения флага; для ожидания заявок используется BlockingQueue в задании 4.
