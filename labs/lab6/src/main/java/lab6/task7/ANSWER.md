Задание 7. Однопроходный отчёт CourseHub

build принимает каталог курсов и одноразовый Stream<Enrollment>. Каталог обязан иметь уникальные коды; повтор кода отклоняется до чтения событий. Enrollment содержит studentId, courseCode и статус ENROLLED или COMPLETED. Конструктор события допускает повреждённые значения для диагностики, а модель Course проверяет свои инварианты.

Одна пара студент–курс считается одной записью. COMPLETED означает, что студент записан и завершил курс; отдельное предварительное ENROLLED не обязательно. Повторы идемпотентны, завершение не отменяется более поздним ENROLLED. Это агрегация фактов участия, без временной истории, отмен и повторных попыток. Поэтому результат одинаков при любой перестановке событий. В реальной модели с отменами потребовались бы время и правило выбора актуального события.

Completion rate = число завершивших / число уникальных записавшихся на курс. Для курса без студентов ставка равна 0. Top-3 содержит только курсы с участниками: убывание completion rate, затем числа завершивших, затем возрастание кода. Распределение по level считает уникальные пары студент–курс, поэтому один студент на двух курсах учитывается дважды. Общий students содержит уникальные положительные id только из валидных событий. Все курсы каталога присутствуют в courses, все уровни присутствуют в byLevel.

Аномалии: null-событие, неположительный studentId, пустой код, неизвестный курс и null-статус. Сохраняется каждое некорректное событие с первой причиной в указанном порядке проверки. Такие события полностью исключаются из метрик. Валидные повторы аномалиями не считаются. Аномалии сортируются по причине, затем по полям события с явным порядком null; карты и множество студентов тоже упорядочены. Неизменяемые копии защищают результат.

Исходный поток читается ровно один раз через collect. Accumulator хранит по одной Boolean-отметке на пару студент–курс, а не все валидные события. Combiner объединяет отметки через логическое ИЛИ и списки аномалий через добавление; finisher упорядочивает результат. Изменения происходят только в собственных накопителях collector: внешние коллекции, сущности и глобальное состояние не меняются. Поддержан и параллельный сбор.

Память последовательного прохода O(C + P + S + A), где C — курсы каталога, P — уникальные валидные пары, S — уникальные студенты, A — все аномалии. От количества повторных валидных событий память не растёт. Точные уникальные студенты требуют хранения id, а полный список аномалий требует O(A): постоянная память при произвольном входе несовместима с этими требованиями. Для parallelStream одновременно существуют частичные накопители, поэтому при строгом лимите памяти следует использовать последовательный stream. Время накопления ожидаемо O(N); завершение добавляет сортировку студентов, курсов и аномалий.

Stream API удобен для collect, фильтрации и ранжирования небольшого результата. Обычный цикл яснее при одновременном построении нескольких итоговых коллекций по каталогу. Повторного прохода по исходным enrollment-событиям нет. Если поток связан с файлом, закрывать его должен вызывающий код через try-with-resources.

Тесты проверяют точные метрики, все виды аномалий, повторы, top-3 и его tie-breakers, пустой вход, неизменяемость, перестановки и parallelStream. Отдельная JVM с -Xmx16m обрабатывает 2 000 000 генерируемых событий для 1000 уникальных пар без накопления входного потока.
