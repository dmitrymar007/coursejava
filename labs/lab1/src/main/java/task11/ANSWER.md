Задание 11. Равенство в иерархии

Нарушение симметричности: equals у Point проверяет instanceof Point, а у ColoredPoint требует ещё и совпадение цвета. Поэтому Point(1, 2).equals(ColoredPoint(1, 2, red)) даёт true, а в обратную сторону false. От порядка вызова зависит результат, например contains в списке.

В этом примере нарушен и контракт hashCode: объекты, равные в направлении Point.equals(ColoredPoint), могут иметь разные хеши, потому что ColoredPoint учитывает цвет.

Исправление 1, строгое равенство: сравнивать getClass() вместо instanceof. Симметричность появляется: Point и ColoredPoint не равны в обе стороны. Цена — даже анонимный подкласс Point с теми же координатами не равен обычной точке. Если контракт Point обещает равенство любых точек по координатам, это мешает подстановке подтипов (LSP). Само использование getClass не означает автоматического нарушения LSP: всё зависит от контракта базового типа.

Исправление 2, композиция: ColoredPoint не наследует Point, а содержит его как поле (оба типа record). Это разные типы, они не равны друг другу в обе стороны, и симметричность сохраняется без оговорок.

Final value class проще: подкласс не может добавить новое значимое для равенства поле. Не нужно согласовывать равенство разных уровней иерархии, но согласованные equals и hashCode всё равно необходимо реализовать. В record они генерируются автоматически. Если нужна точка с цветом как отдельное значение, композиция сохраняет простой контракт обоих типов.
